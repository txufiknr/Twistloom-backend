## Development 1 — Bun 1.4.4 and Node.js 24 security releases

### What happened
Bun 1.4.4 was released October 22. Three high-severity advisories published October 23–24 describe issues fixed in 1.4.4: a Brotli decoder out-of-bounds write, HTTP/3 QPACK amplification, and a compromised eMudhra intermediate-certificate trust problem.

Node.js issued security releases on October 21 for 22.x, 24.x, and 26.x. Node.js 24.22.1 includes the Brotli fix and high-severity DNS/TLS hostname-validation fixes and certificate-store updates.

### Source and date
- [Bun v1.4.4 release notes — October 22](https://bun.com/blog/bun-v1.4.4)
- [Bun Brotli advisory CVE-2026-111497 — October 23](https://github.com/oven-sh/bun/security/advisories/GHSA-663w-cv8g-jj2p)
- [Bun QPACK advisory — October 24](https://github.com/oven-sh/bun/security/advisories/GHSA-cf8x-9m69-3gg3)
- [Bun compromised certificate advisory — October 23](https://github.com/oven-sh/bun/security/advisories/GHSA-26q8-h657-pf84)
- [Node.js October 21 security releases](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases)
- [Node.js 24.22.1 release notes](https://nodejs.org/en/blog/release/v24.22.1)

### Technical details
The Bun Brotli advisory describes possible memory corruption when automatic fetch decompression handles malicious Brotli content. The QPACK issue affects Bun HTTP/3 server paths when HTTP/3 is enabled and fetch paths when HTTP/3 is explicitly requested; it does not imply ordinary HTTP/1.1 or HTTP/2 is affected by that specific issue. The trust-store issue affects TLS validation through Bun's bundled roots.

Node.js 24.22.1 fixes CVE-2026-111497 plus DNS/TLS hostname-validation issues. Bun and Node are separate risk surfaces: the repository uses Bun for build/CI tooling and Node for deployed functions.

### Current Twistloom architecture affected
- `package.json`: Bun 1.3.14 package-manager pin.
- `netlify.toml`: `BUN_VERSION = "1.3.14"`, `NODE_VERSION = "24"`.
- `.github/workflows/ci.yml`: Bun 1.3.14 and frozen-lockfile install.
- Some scheduled workflows use latest Bun, creating version inconsistency.
- Netlify Functions use Node.js; check deployed runtime independently from build tooling.

### Potential benefit
Removes known high-severity vulnerabilities from build/install and CI; reduces TLS trust risk when Bun contacts package registries and APIs; verifies that production functions receive recent Node security fixes.

### Potential drawbacks / risks
Bun 1.4 is a minor-version jump. Lockfile behavior, type definitions, tests, or native dependency installation could change. A major-only Node pin does not prove the deployed patch. The QPACK issue alone is not a reason to disable HTTP/2 or change network architecture.

### Migration / integration complexity
**Low to Medium.** Update the explicit pins to 1.4.4 or newer patched release; reconcile package-manager metadata/lockfile; run frozen install, type checks, lint/import checks, all tests, and a Netlify deploy preview. Verify Node runtime from deployment logs.

### Estimated cost impact
Approximately $0 direct licensing cost. CI/build time may move slightly; measure it rather than assuming a performance gain.

### Performance impact
No application-level performance change is required. Security is the primary reason to upgrade.

### Recommendation
**ADOPT**

- **Impact:** High
- **Effort:** Medium
- **Risk:** Medium
- **Confidence:** High

## Development 2 — OpenAI Decisions API reaches general availability

### What happened
OpenAI announced general availability of the Decisions API with gpt-6-luna on October 22. It is designed for high-volume structured decisions, batched questions, shared input, image-containing questions, and structured JSON input.

### Source and date
- [OpenAI API changelog — October 22](https://developers.openai.com/api/docs/changelog)
- [Decisions API guide](https://developers.openai.com/api/docs/guides/decisions)
- [GPT-6 Luna model details and pricing](https://developers.openai.com/api/docs/models/gpt-6-luna)

### Technical details
The GA announcement raises the supported batch size to 400 questions from 200 during public beta. The endpoint supports structured JSON input and per-question instructions and can reuse shared input across requests. It has a distinct API contract and is not just another Chat Completions model.

The published endpoint pricing notes input at $0.10 per million tokens and says output tokens are not charged for Decisions API requests. Confirm account-specific terms and billing before relying on that estimate.

### Current Twistloom architecture affected
- `src/utils/ai-chat.ts`: provider waterfall, structured-output parsing, and `runEvaluationPass`.
- `src/utils/prompt.ts`: story-page generation and evaluation.
- `src/services/canon-validation.ts`: post-generation continuity/canon checks.
- `docs/roadmap/HYDRAFUSION_IMPLEMENTATION_ROADMAP.md`: measurement-first go/no-go for elaborate critic/orchestration work.

The current orchestrator primarily uses Chat Completions-compatible interfaces. Decisions would be a separate task-specific adapter, not a replacement for prose models.

### Potential benefit
Test focused questions: does a page contradict an established fact; does a StateDelta conflict with prose; does a branch violate a required narrative invariant; does output meet a structured editorial/safety rubric? At $0.10 per million input tokens, 10,000 input tokens would cost roughly $0.001 at the listed rate before other charges/overhead.

### Potential drawbacks / risks
Rubric agreement and false positives may be worse than the current evaluator for nuanced prose. A cheap evaluator can still reject valid experimental writing or approve canon-breaking text. Vendor speed claims may not transfer to Twistloom's context sizes, region, or network.

### Migration / integration complexity
**Medium.** Build an isolated client; compare against the existing evaluator using a fixed corpus and human labels. Measure agreement, false positives/negatives, p50/p95 latency, input tokens, and cost. Keep the existing evaluator as control.

### Estimated cost impact
Potentially low for bounded scoring, depending on context size and call volume. Use measured usage, not list price alone.

### Performance impact
Potentially positive for short classification/rubric tasks. No conclusion for full prose generation.

### Recommendation
**TEST**

- **Impact:** Medium
- **Effort:** Medium
- **Risk:** Medium
- **Confidence:** Medium

## Development 3 — OpenAI adds 12-hour prompt caching to the Responses API

### What happened
On October 20, OpenAI added a selectable 12-hour prompt-cache lifetime for supported Responses API models. It extends reuse of stable prefixes when turns are hours apart.

### Source and date
- [OpenAI API changelog — October 20](https://developers.openai.com/api/docs/changelog)
- [Prompt-caching guide](https://developers.openai.com/api/docs/guides/prompt-caching)

### Technical details
For supported GPT-5.6-and-later models, the documented 12-hour cache write costs 2.5× normal input-token price; cached reads are typically 0.1× ordinary input price on listed models. A 30-minute cache write has a lower 1.25× multiplier. With one cache write and two full cache hits, the simplified input-cost units are about 2.7 versus 3.0 without caching, excluding other charges.

### Current Twistloom architecture affected
- `src/utils/ai-chat.ts` and `src/utils/ai-chat-stream.ts` use Chat Completions-compatible requests.
- Gemini has explicit cached content; Mistral uses a prompt-cache key.
- Existing usage telemetry does not automatically provide Responses API-specific cache-write fields.

### Potential benefit
Could reduce repeated input cost and latency for a dedicated OpenAI task with stable instructions/schema/context and repeated calls within the longer lifetime.

### Potential drawbacks / risks
Not a drop-in option for current transports. Cache writes cost more; unstable prefixes erase savings. A second transport increases maintenance. Caching does not itself improve generation quality.

### Migration / integration complexity
**High** for general orchestration: separate Responses adapter, request mapping, usage normalization, error classification, cache telemetry, and tests. Lower only if an isolated task already warrants direct OpenAI use.

### Estimated cost impact
Potentially positive with repeated cache hits. Measure cache-write tokens, cache-hit tokens, uncached tokens, and cost per task.

### Performance impact
Potentially lower input-processing latency on hits; no expected benefit on misses or output generation.

### Recommendation
**WATCH**

- **Impact:** Medium
- **Effort:** High
- **Risk:** Medium
- **Confidence:** High

### Migration / integration complexity
**Low to Medium.** Update configuration, smoke-test the real SDK path, verify MIME extraction/aspect ratio, and keep a fallback only if it is available. Add a test against documented shutdown IDs.

### Estimated cost impact
Not safely quantifiable from release notes alone. Compare actual image billing and successful-generation rates. Removing failed attempts may reduce wasted calls.

### Performance impact
Expected to improve failure-path latency by removing dead IDs. Benchmark end-to-end image latency and quality.

## Development 5 — Gemini text aliases and introductory pricing deadline

### What happened
Google's October 8 changelog says `gemini-3.7-flash` is deprecated and requests are routed to `gemini-3.8-flash`; `gemini-3.5-flash` is deprecated and routed to `gemini-3.6-flash`. These notices are outside the seven-day window but still affect the live model pools. Introductory pricing for Gemini 3.6/3.8 Flash ends December 31, 2026, with standard rates from January 1, 2027.

### Source and date
- [Gemini API changelog](https://ai.google.dev/gemini-api/docs/changelog) — October 8 notices
- [Gemini latest-model guide](https://ai.google.dev/gemini-api/docs/latest-model)
- [Google Cloud Gemini pricing](https://cloud.google.com/gemini-enterprise-agent-platform/generative-ai/pricing)

### Technical details
The current `src/config/ai-clients.ts` contains older IDs in model selection pools, while `src/utils/ai-cost.ts` stores model-specific estimates. Auto-routing may preserve service availability but can make request-string telemetry and quota attribution diverge from the model actually serving the request.

The documented introductory rate for 3.6/3.8 Flash is $0.75 per million input tokens and $3.75 per million output tokens through December 31; standard rates become $1.50/$7.50 on January 1. Confirm current account pricing before updating estimates.

### Current Twistloom architecture affected
- `src/config/ai-clients.ts`: model pools and per-model limits.
- `src/utils/ai-cost.ts`: cost estimates and cost-spike monitoring.
- AI telemetry and evaluation datasets attributing quality to model IDs.

### Potential benefit
Improves traceability, reproducibility, quota/cost attribution, and budget estimates before the rate change.

### Potential drawbacks / risks
Renaming an alias does not prove better prose quality; the provider already auto-routes. Changing model order or quota limits without traffic evidence could regress reliability. Cost estimators remain estimates, not invoices.

### Migration / integration complexity
**Low.** Update aliases and corresponding cost/quota keys, verify the rate card, and run the story-generation regression corpus. Do not reorder the writing pool solely on release-note claims.

### Estimated cost impact
Potentially significant if affected models account for meaningful token volume: published input/output rates double after the introductory period. Use model-specific token telemetry to estimate.

### Performance impact
No guaranteed improvement from a model alias update alone. Better telemetry improves future latency/quality comparisons.

### Recommendation
**ADOPT**

- **Impact:** Medium
- **Effort:** Low
- **Risk:** Low
- **Confidence:** High

## Development 7 — Tripo AI announces EdenLive real-time generative rendering

### What happened
Tripo AI announced EdenLive on October 20 as a real-time generative renderer for interactive experiences. The company claims 24 FPS or higher on a single consumer GPU and sustained visual synthesis for several minutes.

### Source and date
- [Tripo AI EdenLive announcement — October 20, 2026](https://www.prnewswire.com/news-releases/tripo-ai-announces-major-milestone-in-its-world-model-with-real-time-generative-rendering-for-interactive-experiences-302914408.html)

### Technical details
The announcement describes separating scene/world state from visual rendering: a game engine, simulation, or agent determines events while the renderer generates the visuals. The performance figures are vendor claims. The announcement does not establish a production API, pricing, SLA, licensing terms, or Twistloom-compatible hosted integration.

### Current Twistloom architecture affected
Twistloom is text-first with branching interactive fiction and AI co-writing. Image generation is a separate asset-generation capability; the backend is not a real-time game engine or video renderer.

### Potential benefit
If a stable API becomes available, it could support optional animated scene previews or richer visual-novel experiences without building a renderer in-house.

### Potential drawbacks / risks
GPU/session costs, latency, bandwidth, moderation, asset consistency, client-device constraints, and licensing may conflict with a low-cost creator product. Visuals can drift from canon unless state/character conditioning is reliable.

### Migration / integration complexity
**High.** Requires public API, pricing, concurrency limits, output rights, and a bounded single-scene prototype.

### Estimated cost impact
Unknown; no verified production pricing was established in the announcement.

### Performance impact
Potentially transformative for a future visual mode, but no direct improvement to text generation, RAG, or story-state consistency.
