## Development 1 — Gemini GenerateContent request storage becomes enabled by default for new paid projects

### What happened
Google changed the default for GenerateContent API request storage on October 26, 2026. New paid-tier projects now store GenerateContent, streaming GenerateContent, and batch GenerateContent requests by default. Existing projects retain their prior setting. The request-level store field takes precedence over the project setting.

### Source and date
- [Gemini API release notes — October 26, 2026](https://ai.google.dev/gemini-api/docs/changelog)
- [Logs and datasets guide — current documentation](https://ai.google.dev/gemini-api/docs/logs-datasets)
- [Data logging and sharing policy](https://ai.google.dev/gemini-api/docs/logs-policy)

### Technical details
The request logs are developer-owned data private to the Google project and are distinct from abuse-monitoring logs. The default retention window is up to 55 days, configurable to 7, 14, 28, or 55 days. Paid-tier logs are not automatically used for model training or product improvement; sharing a dataset or feedback with Google is a separate, explicit action. This distinction matters: the change creates project-visible retention, not an automatic training opt-in.

The Google docs state that JavaScript request-level storage control requires @google/genai 2.31.0 or later. The live repository currently resolves 2.21.0. Its GenerateContent calls in ai-chat.ts, ai-chat-stream.ts, and ai-image.ts do not explicitly set store=false. The dormant Interactions implementations already pass store=false.

Twistloom also uses explicit Gemini context caching. Request logging and explicit cached-content resources are separate controls: store=false for logs does not delete or disable a cached-content resource with its own TTL.

### Current Twistloom architecture affected
- package.json and bun.lock: @google/genai is declared as ^2.17.1 and locked at 2.21.0.
- src/utils/ai-chat.ts: non-streaming Gemini GenerateContent request.
- src/utils/ai-chat-stream.ts: Gemini GenerateContent streaming request.
- src/utils/ai-image.ts: native Gemini image generation through GenerateContent.
- src/utils/gemini.ts: explicit cached-content resources and TTL/cleanup remain a separate retention surface.

### Potential benefit
Makes privacy behavior explicit and stable across new Google projects, project recreation, and future default changes. Reduces the chance that story prompts and generated drafts appear in AI Studio logs unintentionally.

### Potential drawbacks / risks
The SDK update may alter types or request validation. Disabling request logs also removes the convenient AI Studio prompt/response trace for those requests; retain the application’s own appropriately redacted telemetry and evaluation fixtures. Do not claim zero data retention: provider abuse monitoring and explicit cached-content resources are separate.

### Migration / integration complexity
**Medium.** Update @google/genai to at least 2.31.0 and regenerate bun.lock; set store=false in each relevant GenerateContent config; keep Interactions’ existing explicit opt-out. Add request-shape tests and perform a small canary. Verify the AI Studio project logging setting as defense in depth.

### Estimated cost impact
No direct model-token price change was announced. Logging may have operational/storage implications, but the source does not establish a new per-request fee. The main value is data governance, not a cost reduction.

### Performance impact
No material model latency or output-quality effect is expected from disabling logs. SDK upgrade performance should be measured rather than assumed.

### Recommendation
**ADOPT**

- **Impact:** High
- **Effort:** Medium
- **Risk:** Medium
- **Confidence:** High

## Development 6 — GitHub AI Scan for repositories enters public preview

### What happened
GitHub announced AI Scan for repositories in public preview on October 28, 2026. This is a whole-repository vulnerability scan, distinct from AI-application-specific pull-request scanning and from CodeQL.

### Source and date
- [AI Scan for repositories in public preview — October 28, 2026](https://github.blog/changelog/2026-10-28-ai-scan-for-repositories-in-public-preview/)

### Technical details
An agentic scanner explores the latest commit on the default branch within a fixed time budget. It focuses on code likely to contain vulnerabilities, skips issues CodeQL already reports when both tools scan the same repository, and places findings in the existing code-scanning alert list. A rescan is required after a fix; alerts do not automatically close simply because a fix was merged.

Eligibility differs by repository ownership and visibility: public repositories owned by personal accounts are supported; private personal-account repositories are not. Organization-owned repositories require Code Security or GitHub Advanced Security for private/internal use. The feature consumes Code Security AI credits; a Copilot license is not required.

### Current Twistloom architecture affected
This is a repository-level security-review option for the backend source, not a production dependency or runtime control. It complements the existing CI and manual review but does not replace the security invariants in AGENTS.md.

### Potential benefit
A bounded, one-off scan may find vulnerability patterns missed by CodeQL rules or current unit tests, particularly in the AI orchestration and API surface.

### Potential drawbacks / risks
Agentic findings can be false positives or incomplete. Fixed time budgets limit coverage, and AI Scan alerts require a rerun after changes to confirm remediation. Credit consumption should be budgeted.

### Migration / integration complexity
**Low.** If eligible, run once against the default branch, triage findings, and validate each candidate manually. No workflow or source-code change is required.

### Estimated cost impact
Consumes Code Security AI credits. GitHub provides SKU-level budgets; verify available credits and the cost forecast before starting.

### Performance impact
No production latency impact. Scan duration is bounded by the configured time budget.

## Development 7 — GitHub adds context-aware AI-detected secret push protection

### What happened
GitHub announced a public-preview expansion of push protection on October 28, 2026. A classifier evaluates how potential secrets are used in surrounding code, rather than relying only on predefined secret formats.

### Source and date
- [Push protection beyond predefined secret patterns — October 28, 2026](https://github.blog/changelog/2026-10-28-push-protection-beyond-predefined-secret-patterns/)

### Technical details
The classifier runs alongside pattern-based detectors and can reject a push when it identifies an AI-detected secret. GitHub reports early results of more than doubling the number of pushes where push protection caught a secret, with user-reported precision comparable to issuer-defined detectors. The feature is off by default and requires both AI-detected secret scanning and push protection to be enabled.

### Current Twistloom architecture affected
The backend integrates multiple provider credentials and payment/authentication secrets. This is a repository hygiene control; it does not replace secret rotation, environment-variable handling, or credential incident response.

### Potential benefit
May catch credentials or tokens that do not match an existing known pattern before they enter Git history.

### Potential drawbacks / risks
Public preview, possible false positives, and plan/feature eligibility requirements. A push rejection must not be bypassed by an agent without authorization.

### Migration / integration complexity
**Low** if the required scanning and push-protection controls are already available. Enable in a controlled repository/organization policy and observe false positives before making it mandatory.

### Estimated cost impact
AI detection consumes AI credits and billing begins when the public preview is enabled. AI-detected post-push alerts remain included with GHSP/GHAS at no additional charge. Confirm entitlement and set an appropriate credit budget before enabling; no production runtime cost.

### Performance impact
Adds a push-time security check; no application runtime impact.

## Development 8 — Vercel Data Cache exits beta and moves to Runtime Cache

### What happened
Vercel announced on October 30, 2026 that Data Cache is exiting beta and moving to Runtime Cache. Next.js fetch caching and unstable_cache migrate without application code changes.

### Source and date
- [Vercel Changelog — October 30, 2026](https://vercel.com/changelog/data-cache-is-moving-to-runtime-cache)

### Technical details
Vercel says Pro projects and environments receive separate Runtime Cache allocations with eight times the previous Data Cache storage; Enterprise receives ten times its previous allocation. Reads and writes that were previously unbilled become billable after migration. Published starting rates are $0.40 per million read units and $4.00 per million write units, varying by region. Hobby includes 1 million reads and 200,000 writes per month. Existing Hobby teams are scheduled to migrate November 29; Pro migration dates are communicated individually.

### Current Twistloom architecture affected
The canonical backend is deployed on Netlify and uses process-local LRU, Upstash Redis, and PostgreSQL-backed cache patterns. This Vercel change only matters to Twistloom’s web/frontend deployment if it uses Next.js fetch caching or unstable_cache on Vercel. The frontend repository/account usage was not inspected here.

### Potential benefit
More isolated per-project cache storage and better observability may improve frontend cache behavior under load.

### Potential drawbacks / risks
Automatic migration means a previously unbilled workload may begin consuming paid read/write units. Existing cache behavior and invalidation remain application concerns; larger capacity is not automatically a reason to cache more.

### Migration / integration complexity
**Low** for assessment. Review cache usage in Vercel Observability, identify high-volume read/write paths, and estimate cost before opting in or the scheduled migration. Do not alter backend Redis/PostgreSQL cache boundaries.

### Estimated cost impact
Potentially non-zero after migration: $0.40/M read units and $4.00/M write units at published starting rates, region-dependent. Actual cost depends on frontend cache traffic and allocation.

### Performance impact
Vercel reports faster performance under load and greater storage; measure the frontend’s hit rate, invalidation behavior, and response latency rather than assuming an improvement.

## Development 10 — Gemini API CLI beta and Computer Use GA

### What happened
Google released the Gemini API CLI beta on October 27 and made the Computer Use tool generally available on October 30 across the Interactions and GenerateContent APIs.

### Source and date
- [Gemini API release notes — October 27 and October 30, 2026](https://ai.google.dev/gemini-api/docs/changelog)
- [Gemini API CLI guide](https://ai.google.dev/gemini-api/docs/cli)
- [Computer Use documentation](https://ai.google.dev/gemini-api/docs/computer-use)

### Technical details
The CLI is described as a stateless, zero-dependency client for AI coding agents, scripts, and CI. Computer Use lets the model propose computer interactions through the supported API. The client application still owns execution, authorization, and safety boundaries; GA does not mean the model should receive unrestricted browser or desktop access.

### Current Twistloom architecture affected
No current backend route or story-generation flow needs computer control. The app’s primary AI behavior is text generation, evaluation, structured memory, and image generation.

### Potential benefit
Could support a future controlled admin/browser automation task or a developer script, but no concrete product or reliability gap is established.

### Potential drawbacks / risks
Computer-use agents can click/type into unintended UI states if execution is not guarded. The CLI’s beta status and additional tool surface are unnecessary operational complexity for the backend.

### Migration / integration complexity
**Medium to High** if integrated into a server workflow; no migration is needed for the current architecture.

### Estimated cost impact
Model/tool usage costs depend on the selected Gemini model and execution pattern; no Twistloom-specific cost advantage is established.

### Performance impact
No expected impact on story-generation latency or memory quality.

### Recommendation
**IGNORE**

- **Impact:** Low
- **Effort:** Medium
- **Risk:** Medium
- **Confidence:** High
